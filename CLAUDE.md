# Gymeri

Платформа для пошуку спортзалів і персональних тренерів (старт: Луцьк). Ролі: client, trainer, gym_owner, admin. Статус: рання розробка, скелет репозиторію.

## Стек

- Backend: Django + DRF, автентифікація через сесії Django (HttpOnly cookie) + CSRF
- База: PostgreSQL
- Frontend: Next.js (App Router), TypeScript strict, pnpm
- Файли: Django `STORAGES` (локально диск, у prod S3)
  Архітектура й хостинг: `README.md`.

## Курсова з ООП (тимчасово)

Проєкт водночас є курсовою з ООП на Python. Головне для неї ООП-ядро backend; frontend це тонкий шар.

- Services оформлюємо класами, доменні виключення будуємо ієрархією.
- Патерни Strategy і Factory застосовуємо там, де вони розв'язують реальну задачу, а не заради патерну.
- Тести й UML-діаграми (у `docs/`) входять у вимоги.

## Команди

Точка входу це Makefile. Локальна розробка йде через Docker.

```
make up | down
make migrate | makemigrations
make test
make lint
```

Якщо потрібної цілі немає, подивись у Makefile, а не вигадуй команду. Перед завершенням роботи запускай `make test` і `make lint`.

## Архітектура

Модульний моноліт: один Django backend (apps: `accounts`, `gyms`, `trainers`, `requests`, `exercises`), Next.js frontend, PostgreSQL. Джерело істини це код.

Кожен app: `models.py`, `services.py`, `serializers.py`, `views.py`, `urls.py`, `migrations/`, `tests/`.
Потік запиту: `views / serializers -> services -> models`.

## Інваріанти

- **Backend не довіряє frontend.** Валідація, права доступу, перевірка власника й бізнес-правила лише в backend.
- **Бізнес-логіка в `services.py`.** Views тонкі. У frontend логіки немає, API routes і server actions для доменних даних не використовуємо. Проксі `/api/*` на backend робимо через `rewrites` у `next.config`, а не через route handlers.
- **Apps спілкуються через services**, а не імпортують моделі один одного.
- **Схема бази змінюється лише через `models.py` + `makemigrations`.** Застосовану міграцію не редагуємо, створюємо нову.
- **Prod не покладається на локальний диск.** Файли йдуть через `STORAGES`; зберігаємо ключ об'єкта, а не повний URL.
- **Секрети лише в змінних середовища.** `.env` не комітимо; нові змінні додаємо в `.env.example`. До браузера потрапляє тільки `NEXT_PUBLIC_*`.

## Конвенції

- Backend: type hints у новому коді; доменні виключення піднімаємо в services, у HTTP-помилки перетворюємо в одному місці; endpoints під `/api/v1/`.
- Frontend: без `any`; публічний каталог (зали, тренери) це server components, client components лише для інтерактивності; усі виклики API через клієнт у `frontend/lib/`.
- Нові залежності додаємо тільки після узгодження.
- Важливі рішення (архітектура, схема бази, контракт API, нові залежності, перейменування) Claude не приймає сам, а спершу уточнює.
- Код і коментарі англійською.
- Зміна поведінки йде разом з тестами.

## Коментарі

Короткі й змістові: пояснюють «чому», а не «що». Якщо код зрозумілий сам, коментар не потрібен. Без очевидних коментарів і закоментованого коду.

## Коміти й гілки

- Англійською, формат Conventional Commits: `<type>(<scope>): <summary>`, наприклад `feat(gyms): add price filter`.
- Типи: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`, `build`, `ci`.
- Заголовок: до 72 символів, наказовий спосіб, з малої літери, без крапки.
- Опис: 1-3 короткі рядки про те, чому зроблена зміна. Один коміт це одна логічна зміна.
- Гілки: `feat/gym-price-filter`, `fix/request-duplicate`.

## Pull requests

- Один PR це одна задача (розмір не обмежений). Перед відкриттям проходять `make test` і `make lint`.
- Опис: **Що** змінено, **Чому** (задача чи проблема), **Як перевірити** (кроки або тести), **Ризики** (міграції, зміни API, що може зламатися). Для змін UI додай скріншот.
- В кінці опису **Деплой**: чи потрібні нові змінні середовища, міграції або особливий порядок розгортання; якщо ні, так і напиши.
- Без змін поза темою PR.
- **Не мерджити PR.** Мердж робить лише головний розробник після перевірки. Без перевірки в prod нічого не потрапляє.

## Деплой

- Деплой автоматичний через GitHub Actions після злиття в `main`, яке робить лише головний розробник: frontend на Vercel, backend на AWS (ECS Fargate).
- Міграції застосовуються під час деплою backend. Міграція має бути сумісною зі старою версією коду: спершу додаємо, видаляємо вже наступним релізом.
- Секрети задаються в налаштуваннях Vercel і AWS, а не в репозиторії. У prod: `DEBUG=False`, лише HTTPS, CORS тільки для домену frontend.
- Не запускай деплой, не змінюй CI та інфраструктуру, не мерджи й не пуш у `main`. Працюй у гілці й відкривай PR.
